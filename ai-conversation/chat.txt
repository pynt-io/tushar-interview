     ② path:    segmentMatch(rule.Target.PathPattern, endpoint.Path)

  Path algorithm — split both on /, compare segment-by-segment:

  pattern:  /users/{userId}        →  ["users", "{userId}"]
  endpoint: /users/{userId}        →  ["users", "{userId}"]

  Rules per segment:
    len mismatch                      → NO match   (this kills /admin/* vs
  /admin/a/b)
    pattern seg == "*"                → match ANY one segment
    pattern seg == "{xxx}"            → match ANY one segment (template
  placeholder)
    else                              → must be exact string equal

  func segmentMatch(pattern, path string) bool {
      p := strings.Split(strings.Trim(pattern, "/"), "/")
      e := strings.Split(strings.Trim(path, "/"), "/")
      if len(p) != len(e) { return false }          // ← wildcard = exactly one 
  segment
      for i := range p {
          seg := p[i]
          if seg == "*" || (strings.HasPrefix(seg,"{") &&
  strings.HasSuffix(seg,"}")) {
              continue                               // wildcard / param → any
          }
          if seg != e[i] { return false }            // literal must match
      }
      return true
  }

  That single len(p) != len(e) line is what enforces "* matches exactly one 
  segment."

  ---
  3. Mutation — the key insight

  You spotted the real complexity: path.userId, query.userId,
  header.Authorization, body.user.address.id are all "a value at some location"
  but the location behaves differently. Don't build a separate strategy per
  combination — that explodes into parameter_swap×path, parameter_swap×query,
  parameter_swap×body…

  Split it into TWO orthogonal axes:

     AXIS A: WHERE is the value?          AXIS B: WHAT do we do to it?
     (the target domain)                  (the mutation strategy)
     ─────────────────────────           ────────────────────────────
     path.userId    → PathAccessor        parameter_swap → get value,
     query.userId   → QueryAccessor                        apply strategy
     header.Auth    → HeaderAccessor                       (increment), set
     body.a.b.c     → BodyAccessor        header_inject  → set value directly

     Accessor.Get(req, fieldPath) → value
     Accessor.Set(req, fieldPath, newVal) → req'

  The mutation strategy never knows how to reach into a nested body — it just
  asks the Accessor to Get/Set. This is the design that scales: a new domain =
  one new Accessor; a new strategy = one new Mutator. They compose.

  target string  "body.user.address.id"
                  │      └──────┬───────┘
               domain        fieldPath
            → BodyAccessor   → walk nested JSON via dot-path

  The target parser (one place):

  // "body.user.address.id" -> ("body", "user.address.id")
  func parseTarget(t string) (domain, fieldPath string) {
      parts := strings.SplitN(t, ".", 2)
      return parts[0], parts[1]
  }

  Nested JSON walk (your body concern):

  // BodyAccessor.Set walks a map[string]interface{} by dot path
  // "user.address.id" descends body["user"]["address"]["id"]
  func (BodyAccessor) Set(body map[string]any, path string, val any) {
      keys := strings.Split(path, ".")
      m := body
      for _, k := range keys[:len(keys)-1] {
          m = m[k].(map[string]any)      // descend (real code: guard type + 
  existence)
      }
      m[keys[len(keys)-1]] = val         // set leaf
  }

  Flow inside mutate for one rule+endpoint:

  orig := Request.FromEndpoint(ep)
  for each mutation m in rule.Mutations:
      domain, field := parseTarget(m.Target)
      accessor      := accessorRegistry[domain]     // path/query/header/body
      strategy      := mutatorRegistry[m.Type]      //

                       │
                       ├ parameter_swap+increment: cur=accessor.Get; make cur+1,
  cur-1;
                       │                             clone orig, accessor.Set
  each → 2 variants
                       └ header_inject:            clone orig,
  accessor.Set(field, m.Value) → 1 variant

  5 & 6. Multiple specs + where concurrency belongs

  independent fan-out points:

     FAN-OUT A: multiple spec files          FAN-OUT B: sending mutated requests
     (embarrassingly parallel, no shared     (network I/O — the classic case for
      state — each spec → own results)        a BOUNDED pool so you don't DoS
  the
                                              customer's API)

     specs ──┬─ spec1 ─┐                      variants ──▶ [ sem chan, N slots ]
             ├─ spec2 ─┼─▶ merge results                    │  │  │
             └─ spec3 ─┘                                     ▼  ▼  ▼
                                                          HTTP  HTTP  HTTP

  And your final question — is post-mutation the right place for concurrent 
  HTTP? Yes, unambiguously. Load/Match/Mutate are pure, in-memory, microseconds
  — parallelizing them adds bug surface for zero gain. The send step is slow,
  blocking, I/O-bound, and touches a real customer server. That's textbook
  goroutine + bounded semaphore territory:

  sem := make(chan struct{}, maxConcurrency)   // tunable: rate-limit the blast
  var wg sync.WaitGroup
  for _, v := range variants {
      wg.Add(1)
      sem <- struct{}{}                        // acquire slot (blocks if N in 
  flight)
      go func(v Request) {
          defer wg.Done()
          defer func(){ <-sem }()              // release slot
          resp := send(v)
          detect(rule, resp)                   // detection lives here, with a 
  real response
      }(v)
  }
  wg.Wait()

  maxConcurrency is your safety valve — exactly the "fine-tuning so we don't
  overload the server" you wanted. And notice detection naturally lives right 
  here, because only now do you have a real response to test against.

          ▼

  2. Mock server — great idea, but use httptest, not Gin 🎯

  The instinct is excellent: a mock target turns detection from "nice-to-have 
  (no server to hit)" into a working end-to-end demo. That's exactly the "runs
  end-to-end on test data" the README rewards.

  But Gin is the wrong tool here. Reasons:

     Gin server                          httptest.Server (stdlib)
     ──────────────                      ─────────────────────────
     ✗ new dependency in go.mod          ✓ zero deps (net/http/httptest)
     ✗ separate process to start/stop    ✓ in-process, starts/dies with the CLI
     ✗ contradicts "not a long-running   ✓ ephemeral: spins up, serves, exits
       service" in the README            ✓ real HTTP round-trip on a real
  localhost URL
     ✗ manual port/lifecycle mgmt        ✓ auto-assigned port via srv.URL

  httptest.Server gives you a real HTTP server on a real port, in the same
  binary, that vanishes when the program exits — perfectly matching "it runs, 
  produces output, and exits." You get the full round-trip (real detection)
  without a second process or a dependency.

  // spin up a mock target that behaves "vulnerably" so detection fires
  mux := http.NewServeMux()
  mux.HandleFunc("/users/", func(w http.ResponseWriter, r *http.Request) {
      w.WriteHeader(200)
      w.Write([]byte(`{"id":43,"email":"victim@example.com"}`)) // triggers BOLA
  detection
  })
  mux.HandleFunc("/admin/", func(w http.ResponseWriter, r *http.Request) {
      if r.Header.Get("Authorization") == "" {
          w.WriteHeader(200)                                     // triggers 
  AUTH-BYPASS
      } else {
          w.WriteHeader(403)
      }
  })
  srv := httptest.NewServer(mux)
  defer srv.Close()
  baseURL := srv.URL   // e.g. http://127.0.0.1:52413  → prepend to mutated 
  paths

  Because there are no payloads (routes only, as you said), the mock is trivial
  — you just script each route's status/body to represent a vulnerable-or-not
  target, and detection reads it back.

  ▎ If you specifically want to show off building a Gin service, keep it as a 
  ▎ separate optional demo target behind a --target flag, and default to the 
  ▎ in-process httptest one. But for the core deliverable, httptest is cleaner 
  ▎ and faster to get running.
